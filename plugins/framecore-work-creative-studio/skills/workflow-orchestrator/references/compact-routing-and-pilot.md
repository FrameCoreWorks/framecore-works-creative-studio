# Compact routing and optional project review

Use the [working contract](studio-contract.md) and [integration authority](../../pipeline-core/references/studio-integration-policy.md). Read this chapter when a simple request starts accumulating unnecessary documents, or when the user wants to measure whether the Studio helps in an actual project. Source rationale: [C11 and C12](../../research-evidence/references/creative-upgrade-sources.md).

## Load for the next decision

| Request | Smallest useful working set | Stop before |
|---|---|---|
| Quick ideas | Relevant creative owner, evidence for the unchanged/new question, actual product locks and relevant taste records | Full storyboard, prompt packs, production manifests unless requested |
| Selected concept to shots | Sequence owner, selected concept, relevant product/character sources and adjacency checks | Reopening the concept or writing every provider's syntax |
| One prompt | Prompt owner, requested target evidence, exact locks, actual attachments | New campaign ideation or unnecessary onboarding |
| Existing defect | Appropriate media/copy reviewer, actual accessible artifact, reported failure and preservation set | Whole-library loading or unrelated repairs |
| Execute an approved plan | Exposed tool route, active scoped authorisation, bound inputs, verification/retry limits | Unrequested providers, uploads or paid fallbacks |

Carry a compact handoff: task/stage, selected mechanism, exact locks, available input aliases, source evidence relevant to the next decision, changed fact and next action. Link to existing project resources rather than copying every chapter. Reuse already-read evidence for an unchanged question. Do not drop required source truth merely to shorten context. A small requested correction should remain small.

Keep 37 canonical skill entrypoints as the active registry. The workflow-kit reference mirror is not another installation. Its former SKILL.md files are inert pointers; exact upstream entrypoint bytes live in SKILL.source.md and the source archive. For explicitly requested upstream installation/testing, extract the archive to a separate workspace rather than treating the reference mirror as executable upstream state.

## Optional project review, only when requested

A pilot or evaluation exercise requires an explicit request. Do not propose or run one when the user declines it, and do not require a client brief, media or pilot before improving the plugin. Continue authorized development from identified gaps, source-backed methods and bounded structural checks. An ordinary creative request remains ordinary production work; do not relabel it as an experiment. Use the steps below only for a requested project review.

1. Capture the requested deliverable and what success means to the user.
2. Present the requested number of short directions, after the applicable research gate.
3. Record the exact selection or rejection and the user's stated reason. One unexplained rejection gets one useful question.
4. Develop the selected route into shots and examine adjacent pairs.
5. Compile only the requested target prompts. Execute only when the actual operation and scope are authorised.
6. Review actual outputs when accessible. Log defects separately from taste changes and unsupported assumptions.
7. Stop at the requested deliverable. Save only the useful project decisions in the authorised destination.

## Measures with a defined meaning

For an explicitly requested evaluation, use the [pilot record](../assets/project-pilot.template.json). Count directions actually shown, meaningful feedback turns, source-lock violations in inspected outputs, and repairs to shot transitions. Record whether the first selected concept survived production. Record time only when actually observed or supplied; do not invent seconds saved or predicted engagement. Keep unmeasured values Unknown.

Separate automatic structural checks, assistant editorial judgment and the user's decision. A higher acceptance count does not prove objective artistic quality. A synthetic prompt response does not establish real client satisfaction. Add a regression case only for a demonstrated failure or a material risk; do not multiply tests simply to increase a score.
